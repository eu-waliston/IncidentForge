Capabilities

Everything a blue team needs to practise the full lifecycle

From raw event ingestion to explainable risk scoring and simulated containment.

🗂️

Incident Management

Create, inspect, filter, and update incidents with validated status transitions across the full lifecycle.

📥

Event Ingestion

Normalize individual or batch events, validate input, and deduplicate using source identifiers where available.

🔐

Evidence Vault

Store evidence metadata and content, calculate SHA-256 hashes, and record chain-of-custody operations.

🧠

Correlation Engine

Identify related events via shared assets, actors, tags, event characteristics, and a configurable time window.

📊

Risk Engine

Produce an explainable risk score using event severity, related-event count, and correlation strength.

📜

Playbooks

Run predefined phishing-triage and endpoint-alert workflows in simulation mode — no real containment.

🖥️

Investigation Dashboard

Browse incidents, events, evidence, correlations, and playbook runs from a React + Vite interface.

🛡️

Security Baseline

Helmet, configurable CORS, request IDs, payload limits, rate limiting, optional API token, container hardening.

Getting started

Running in minutes

Node.js 22+, npm, and MongoDB 7+ locally or through Docker.

⚠️

Simulation mode by default

Response playbooks do not isolate endpoints, block accounts, or perform real-world containment actions. Use synthetic lab data unless the environment is explicitly approved and secured for sensitive evidence.

1 · API
# clone and configure
git clone <YOUR_REPOSITORY_URL>
cd IncidentForge
cp .env.example .env
npm install

# set a valid MongoDB connection string in .env
npm run check
npm test
npm run dev

API defaults to http://127.0.0.1:3000 · health check at GET /health

2 · Dashboard
# in a second terminal
cd frontend
cp .env.example .env
npm install
npm run dev

Vite normally serves the dashboard at http://localhost:5173. Check frontend/.env.example for the API URL setting.

docker compose
# review .env.example, create .env, use strong local secrets

docker compose up --build

Stop with Ctrl+C or docker compose down. Persistent database and evidence storage are configured through Compose volumes. Inspect docker-compose.yml before changing port bindings or deploying elsewhere.

When API_ACCESS_TOKEN is configured, requests must include the x-api-token header.

POST /api/events — example submission
curl -X POST http://127.0.0.1:3000/api/events \
  -H 'Content-Type: application/json' \
  -H 'x-api-token: YOUR_LOCAL_TOKEN' \
  -d '{
    "source": "lab-sensor",
    "sourceEventId": "demo-evt-001",
    "type": "authentication_failure",
    "severity": "medium",
    "asset": "workstation-01",
    "actor": "analyst-lab",
    "tags": ["training", "authentication"]
  }'

Adjust payload fields to the validation rules in src/. Never commit real tokens or secrets.

Security first

A learning lab — not a certified product

Address these limitations before exposing IncidentForge to a network or using it with sensitive evidence.

Authentication & authorization

The optional shared API token is not a substitute for individual identities, RBAC, session management, or a complete authorization model.

Rate limiting

The current in-memory limiter is process-local and resets on restart. Distributed deployments need a shared store and edge-level controls.

Evidence integrity

SHA-256 hashes help detect content changes, but the app provides no immutable / WORM storage. A privileged admin may alter evidence or custody records.

Playbook safety

Response actions are simulations. No real endpoint isolation, account disablement, email delivery, or network blocking is performed.

Deployment

Use TLS, managed secrets, restricted network access, least privilege, backups, monitoring, dependency updates, and a security review before production.

Sensitive data

Use synthetic lab data by default. Do not upload real credentials, personal data, or evidence unless the environment is explicitly approved and secured.
